# 产品案例与演示提纲

## 项目是什么

这是在业余时间与AI协作推进的个人报告文本一致性工作台。选题借助影像设备行业接触，目标是把场景、需求、工作流、规则与模型取舍、验收及交付走通，展示产品经理判断，不冒充雇主研发项目或医院上线。

## 四项可以被追问的取舍

1. 从左右单模块扩为三规则和完整闭环，是回应求职作品需要，范围仍限定文本，不做全医院平台。
2. 规则先出、AI手动追加，让已有任务不被模型等待或失败挡住；同时能观察是否值得付费补充。
3. 无候选、不确定、失败和来源分开；同题合并不是投票，反馈不是已改报告，修改后必须复检。
4. 先冻结输入/标签再评测，区分正确跳过与真正比较，不把合成草案符合度说成临床准确率。

## 五分钟演示

第一分钟说清两段输入、直接用户任务和边界。第二分钟演示尺寸冲突、证据与人工修改。第三分钟看等值复检和多病灶跳过。第四分钟看反馈、管理和导出。第五分钟打开评测页，展示一条正常、一条无法比较、一条未标注，再说明真实模型证据与待做项。

没有本机Key时，不为演示假装实时AI；展示历史实验说明和模拟联调截图，明确各自来源。网络或模型失败也可继续演示规则与产品过程。

## 人与AI的贡献

候选人已提供行业场景、作品目标与范围要求，确认时间/预算，完成命令行模型实验及网页规则部分验收。10月20日本人隐藏配置Key，由AI在独立浏览器完成2次真实网页DeepSeek开发验证。数量例找到候选却分类错误，产品随后增加“类别待核对”兜底并离线验证，保留失败不重抽。AI承担大量方案、代码与技术验证；完整本人体验、独立解释和演练仍待完成，不能将代码产物写成熟练全栈、精通RAG或带领研发团队。

## 练习追问

- 你怎样知道医院需要？目前只是假设，未完成医生访谈或价值验证；下一步需具体任务观察与反馈。
- 为什么用了模型还扩规则？实验指出的两类明确表达能被低成本受限规则覆盖，模型增量需重新验证。
- 34/34代表什么？是有标签合成案例对草案契约符合，含正确跳过，不是临床准确率。
- 为什么不自动改？文本矛盾不能证明哪段医学上正确，最终判断与修改仍归人。
- 你本人做了什么？按已有行为举证，并区分AI产物、辅助操作与独立掌握；未做的不提前认领。

公开前补本人实际操作与解释证据，再更新这里的状态。不要背一段没有做过的项目故事。
